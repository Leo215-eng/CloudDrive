# FastDFS 双 Storage 分布式存储独立验收测试方案

## 1. 文档目的与独立性

本方案由验收视角编写，不描述具体代码或容器如何实现，而是定义上线前必须证明的业务行为、失败边界、证据和判定规则。验收执行人应尽量不参与实现；若同一人执行，至少应按本方案逐项留存原始证据，不能以“容器已启动”代替业务验收。

验收对象是网盘文件服务接入 FastDFS 后的文件存储能力，目标为验证：文件本体从业务数据库分离、同组双 Storage 副本可用、异常时不会造成越权访问或错误删除、业务数据与物理文件状态可追溯。

## 2. 验收范围与边界

### 覆盖范围

1. 文件服务经 FastDFS 完成普通上传、访问/预览、下载和物理删除。
2. `1 Tracker + 2 同组 Storage` 环境中，同一文件在两个 Storage 形成可校验的副本。
3. 网盘真实业务场景：用户隔离、文件重名、秒传引用、回收站恢复、分享访问（若现有分享服务可启动）。
4. 异常与兜底：Tracker 不可用、单 Storage 不可用、副本同步延迟、重复请求、下载/删除失败和临时文件清理。
5. 文件元数据、用户文件关系和 FastDFS 逻辑路径的一致性。
6. 单机开发环境下的性能边界与容量保护，不将本次结果宣称为生产压测容量。

### 不作为通过前提

- Tracker、Storage 跨机房容灾、组件集群选主和生产级 SLA。
- ES、Canal、RocketMQ、AI/向量检索等非文件存储依赖。
- 多设备本地目录同步、版本冲突解决。
- 未部署的分享或回收站服务的端到端页面测试；对应项应明确标记为“环境未覆盖”，不得伪造通过。

## 3. 业务验收基线

### 测试角色与数据

| 角色/数据 | 用途 | 要求 |
|---|---|---|
| 用户 A、用户 B | 验证用户文件关系及权限隔离 | 两个独立账号，不在文档写入真实凭据 |
| 文件 F1 | 普通上传与副本校验 | 10–50 MB，保存 SHA-256 值 |
| 文件 F2 | 分片/恢复链路 | 100–500 MB，至少切分为 10 个分片 |
| 文件 F3 | 同内容不同文件名 | 与 F1 内容相同，用于秒传/去重语义验证 |
| 文件 F4 | 边界文件 | 空文件、中文名、空格名及 4 GB 上限以下大文件各一个 |

所有测试文件应为无敏感信息的随机或公开样例。每次验收记录文件名、大小、SHA-256、上传用户、业务文件 ID 和 FastDFS `group + path`；不要把 Token、密码或内部地址写入文档。

### 关键一致性原则

1. 用户可见性以“用户—文件关系”和鉴权结果为准，不能仅凭相同 MD5 或相同 FastDFS 路径授予访问权限。
2. FastDFS 路径是物理文件定位信息；用户删除进入回收站不得直接删除仍被其他有效记录引用的物理文件。
3. 对外访问 URL 只能由服务端依据受控逻辑路径生成；不得接受客户端提交的任意 Storage 路径作为下载/删除目标。
4. 双 Storage 的副本同步允许短暂延迟，但最终副本内容必须与源文件校验一致。

## 4. 准入条件与退出条件

### 准入条件

- 两个 Storage 均注册在同一组，Tracker 状态显示在线。
- 文件服务已明确启用 FastDFS 存储引擎；本地/OSS 引擎不会被误注入为实际写入实现。
- MySQL、Redis、Nacos 与文件服务处于可用状态；测试账号可获取合法登录态。
- 验收前记录容器版本、服务 Git commit、配置 Profile 和测试时间。
- 确认测试卷与本地文件存储目录可区分，避免把历史文件当作本轮副本证据。

### 退出/阻断条件

发生以下任一情况，停止“通过”判定并创建问题记录：

1. 未授权用户能通过猜测 `group/path` 获取、删除或替换他人文件。
2. 双副本最终内容不一致、下载内容 SHA-256 不匹配，或文件服务写入的路径无法定位真实文件。
3. 单节点异常导致已完成文件无告警地丢失，或恢复后产生同路径不同内容。
4. 回收站/秒传场景直接删除仍被有效用户文件关系引用的物理文件。
5. 任意验收命令需要暴露真实密钥、Token 或生产地址才能执行。

## 5. 验收用例

### A. 基础功能与业务闭环

| 编号 | 场景与步骤 | 预期结果 | 必须留存的证据 | 通过标准 |
|---|---|---|---|---|
| F-01 | 用户 A 上传 F1，获取业务文件 ID、逻辑路径和访问地址 | 上传成功；数据库仅保存元数据和 FastDFS 逻辑路径，不保存大二进制字段 | 接口响应脱敏截图、DB 查询结果字段截图、文件 SHA-256 | 三处路径/文件 ID 可关联，下载内容校验一致 |
| F-02 | 使用文件列表、预览、下载入口访问 F1 | 文件可列出、可预览的类型正常预览、下载文件可打开 | 页面或接口结果、下载文件 SHA-256 | 与上传前 SHA-256 完全一致 |
| F-03 | 用户 A 连续两次提交同一上传/合并请求 | 不产生重复用户文件、重复物理对象或服务异常 | 数据库记录数、服务日志中的请求 ID | 结果幂等；返回既有结果或明确业务提示 |
| F-04 | 上传同内容但不同名称 F3；分别由 A、B 发起 | 秒传/去重仅复用物理文件时，仍分别建立正确用户关系与文件名 | 两用户文件列表、文件关系记录、物理路径 | B 不能在未建立关系前访问 A 的私有文件；建立关系后仅可访问自己的条目 |
| F-05 | 上传中文名、空格名、无扩展名和空文件 | 服务正确处理元数据、路径和下载响应头 | 接口结果、下载文件名 | 不乱码、不路径穿越、不错误识别为已有文件 |

### B. 双 Storage 副本与故障切换

| 编号 | 场景与步骤 | 预期结果 | 证据 | 通过标准 |
|---|---|---|---|---|
| R-01 | 上传 F1 后，按 FastDFS 路径在 Storage-1、Storage-2 分别定位文件 | 两节点均存在目标文件 | 两节点文件清单、各自 SHA-256、Tracker 状态 | 两份 SHA-256 与源文件相同；允许在约定等待窗口内轮询 |
| R-02 | 连续上传 10 个不同文件，等待同步完成 | 每个文件均有两个副本，无遗漏或错配 | 路径与校验值对照表 | 20 个副本均完整；任一遗漏即失败 |
| R-03 | 暂停 Storage-1 后，对已完成的 F1 执行访问/下载 | 不应读取到损坏内容；若访问层未具备多节点故障切换，必须返回明确失败而非假成功 | 容器状态、请求结果、下载 SHA-256、日志 | 已知能力范围内结果可解释；“另一副本仍存在”必须得到验证 |
| R-04 | 恢复 Storage-1，观察节点上线和既有文件一致性 | 节点重新注册；F1、F2 副本无差异 | Tracker 状态、两端 SHA-256 | 两端内容一致，未出现同路径不同内容 |
| R-05 | 暂停 Storage-1 时发起新上传 | 系统按实际能力明确成功或失败；若成功，恢复后应补齐副本；若失败，不创建半完成业务记录 | 上传响应、元数据状态、恢复后副本检查 | 不允许“接口成功但无可用物理文件” |

**副本等待窗口：** 本地环境首次取 `60 秒`，每 `5 秒`检查一次；超过窗口仍未同步为失败。该窗口只是验收阈值，不是生产同步 SLA。

### C. 异常、兜底与数据一致性

| 编号 | 场景 | 预期兜底行为 | 通过标准 |
|---|---|---|---|
| E-01 | Tracker 不可用时上传 | 上传请求快速失败或在配置重试后失败，返回可识别错误；不得写入“已完成”文件记录 | 无孤儿元数据；恢复后可重新上传 |
| E-02 | Storage 写入中断/网络超时 | 后端不把未确认写入标记为完成；客户端可根据分片状态续传 | 分片记录与实际文件状态可解释，不重复合并 |
| E-03 | 合并接口并发调用 | 同一 `userId + identifier` 只允许一个有效合并过程；其他请求复用结果或被明确拒绝 | 最终仅一条有效文件记录、一个逻辑路径 |
| E-04 | 分片上传完成但前端未调用合并 | 临时分片在过期策略后被清理或可继续恢复；不会伪造完整文件 | 清理前可查进度，清理后无可下载完整记录 |
| E-05 | 删除请求重复/并发 | 删除操作幂等；物理删除前检查引用与回收站状态 | 不误删其他用户或分享仍引用的物理文件 |
| E-06 | 已删除文件恢复 | 恢复后用户关系、逻辑路径与物理文件一致；若物理文件不存在，返回可追踪异常而非空成功 | 恢复结果与下载 SHA-256 一致 |
| E-07 | 伪造他人业务文件 ID 或 FastDFS 路径 | 服务端基于登录用户和业务关系校验，拒绝越权访问、下载和删除 | 返回 401/403/业务无权限码，目标文件不受影响 |
| E-08 | HTTP 访问层不可用 | 预览/下载出现可诊断错误；元数据不被删除或改写 | 接口错误可定位，恢复访问层后文件可正常访问 |

### D. 性能边界与资源保护

本阶段只验证开发笔记本可承受的边界，不输出“生产 QPS”或“高可用 SLA”。测试时只启动文件服务和必要基础设施，停止 ES、AI、RocketMQ 等无关重型组件。

| 编号 | 测试 | 建议负载 | 观察指标 | 通过标准 |
|---|---|---:|---|---|
| P-01 | 普通上传 | 10 个 10–50 MB 文件串行 | 成功率、SHA-256、磁盘空间、容器重启次数 | 全部成功，无容器 OOM 或重复记录 |
| P-02 | 分片上传与合并 | 1 个 100–500 MB 文件，至少 10 分片 | 分片状态、合并耗时、临时目录清理 | 合并后校验一致，无残留完成态分片 |
| P-03 | 轻量并发 | 5 个用户/任务同时上传不同 10 MB 文件 | 错误率、重复路径、锁等待、两端副本 | 5 个文件均完整，错误应可重试且无数据串写 |
| P-04 | 失败恢复 | 在第 60% 分片后中断，再恢复 | 已上传分片识别、重复传输量 | 仅补传缺失分片，最终内容校验一致 |

性能结果需记录实际机器配置、服务版本、并发、文件大小、网络条件和原始摘要；不将一次本地结果外推到日均上传量、10 万级索引或生产环境。

## 6. 验收证据包

每次验收建立一个日期目录或附件包，至少包含：

1. 环境清单：Git commit、容器镜像/状态、启用 Profile、测试时间。
2. 用例执行表：编号、执行人、结果、失败原因、重试次数。
3. 文件校验对照表：源文件、Storage-1、Storage-2、下载文件的 SHA-256。
4. 脱敏接口响应、关键日志片段、Tracker 节点状态和两 Storage 文件存在性证据。
5. 数据库查询结果：只保留必要字段和脱敏后的业务 ID，不导出用户隐私数据。
6. 异常演练记录：停止/恢复的目标组件、影响、恢复时间、未解决限制。
7. 性能边界摘要及原始数据文件的本地保存位置。原始 `.jtl`、日志、Token 和测试文件不得提交 Git。

## 7. 总体验收判定

### 通过

同时满足以下条件：

1. F、R、E 类所有“必须通过”用例通过；P 类至少完成 P-01、P-02、P-04。
2. 双 Storage 对至少 10 个文件完成副本校验，且源文件、两副本、下载文件的 SHA-256 一致。
3. 单节点故障、重复请求、未合并分片、越权访问、删除/恢复均有可验证结果，未发现 P0/P1 数据安全问题。
4. 已知限制明确记录，例如 HTTP 访问层是否支持自动切换；限制不能被包装成已实现的高可用能力。

### 有条件通过

核心上传、双副本和权限隔离通过，但某个非核心能力（如分享服务未部署、Nginx 自动切换未实现）未覆盖。必须在验收报告中列出缺口、影响与补测计划；对外描述仅限已验证部分。

### 失败

任一退出条件触发，或关键用例无法提供证据，即验收失败。失败后不得通过删除数据、手工修改数据库或只重跑成功场景掩盖问题；应按问题闭环模板记录并回到设计/实施阶段修复。

## 10. 执行记录

### 2026-07-26：阶段 A 基础设施独立验收

**执行边界：** 本次仅验收 Docker 中的 Tracker、双 Storage、FastDFS 客户端和 Storage-1 内置 HTTP 访问层；未启动文件服务或其他应用服务，未修改业务代码、配置或编排文件。未删除任何命名卷。测试样本为无敏感内容的 96 B 文本文件，其 SHA-256 为 `D5228FA70A336E407E963BA180FB467CFE7E5B1DEAEB09DB816D5C8048CE7D09`。

| 检查项 | 实际命令/操作 | 实际结果 | 判定 |
|---|---|---|---|
| 容器健康状态 | `docker ps -a` | Tracker、Storage-1、Storage-2 均为 `healthy`；两个 Storage 位于同一 Docker 网络并挂载独立命名卷 | 通过 |
| Tracker 节点识别 | 在 Tracker 容器使用临时客户端配置执行 `fdfs_monitor` | `group1` 中共 2 个 Storage，初始状态均为 `ACTIVE`，可读和可写节点数均为 2 | 通过 |
| 测试文件上传 | 创建临时样本，复制至 Tracker 容器；`fdfs_upload_file` 上传 | 成功返回 `group1` 下的逻辑路径；上传后 Tracker 计数可观察到写入 | 通过 |
| 双副本校验 | 分别在两个 Storage 计算对应物理文件 SHA-256 | 两端均存在文件，校验值与源文件完全一致 | 通过 |
| HTTP 访问 | 经 Storage-1 暴露的 HTTP 入口下载样本 | 返回 HTTP 200、下载大小 96 B、SHA-256 与源文件一致 | 通过 |
| Storage-2 停止演练 | `docker stop networkdisk-fastdfs-storage-2`；重新执行 `fdfs_monitor` 和 HTTP 下载 | Tracker 显示 1 个可读/可写节点，Storage-2 为 `OFFLINE`；Storage-1 的 HTTP 下载仍返回校验一致的文件 | 通过（见限制） |
| Storage-2 恢复演练 | `docker start networkdisk-fastdfs-storage-2`，轮询 `fdfs_monitor`，复查两端 SHA-256 | 首次 5 秒轮询时已恢复为 2 个可读/可写 `ACTIVE` 节点；既有副本两端校验一致 | 通过 |

**物理路径校验说明：** FastDFS 返回的是包含存储卷标识的逻辑路径，例如 `M00/...`；Storage 容器内 `store_path0` 对应的物理定位应去除 `M00/` 前缀后再拼接。首次检查错误地把完整逻辑路径直接拼到 `/var/fdfs/data`，导致“文件不存在”；按 FastDFS 路径映射修正检查方式后，两份副本均验证通过。这是验收脚本/人工检查的路径理解问题，不是副本同步失败。

### 已发现限制与待处理项

1. **默认客户端配置存在主机名不一致风险：** 容器内默认 `client.conf`/`storage.conf` 的 Tracker 主机名为 `tracker`，而 Docker 编排服务名为 `fastdfs-tracker`。本次独立客户端验收使用容器 `/tmp` 中的临时配置，将 Tracker 目标改为可解析的服务名；未改动持久化配置。应用接入前必须由实施方确认实际客户端配置使用可解析地址，否则文件服务端到端上传会被阻断。
2. **HTTP 故障切换尚未证明：** 对外 HTTP 入口只发布自 Storage-1 的 Nginx。停止 Storage-2 后下载仍成功，仅证明 Storage-1 副本和服务可用，**不证明** Nginx 能在 Storage-1 故障时自动路由到 Storage-2。该项需在访问层具备多节点路由后另行验收。
3. **应用端到端验收未执行：** 未验证用户鉴权、数据库元数据、用户—文件关系、分片合并、秒传、回收站、分享、删除幂等或越权拦截；这些用例不得标记为通过，需待文件服务可启动且接入 FastDFS 后执行。
4. **测试样本仍保存在两个命名卷中：** 为保留副本校验证据，本次未执行物理删除。后续由实现/运维人员按测试数据清理流程处理，不得将清理操作与验收结论混淆。
5. **未进行性能结论：** 本次只上传 1 个 96 B 样本以验证基础设施路径与副本；未开展容量、并发、分片或大文件性能测试，不能用于任何吞吐或 SLA 表述。

### 阶段结论

阶段 A 基础设施验收 **有条件通过**：`1 Tracker + 2 同组 Storage` 的注册、文件上传、双副本内容一致性以及 Storage-2 停止/恢复均得到独立证据验证。通过结论仅限基础设施层；由于默认客户端配置风险和应用服务未启动，文件服务的端到端接入验收仍为未通过/未执行状态。

**只读基线：** 当前编排存在独立 `fastdfs-access-nginx` 容器，对宿主机发布 `8888`；其运行中的 Nginx 配置包含两个 Storage 上游、连接/读取超时和 `proxy_next_upstream` 被动重试规则。该配置仅证明具备访问层切换条件，实际可用性以下方故障演练结果为准。

| 检查项 | 实际命令/操作 | 实际结果 | 判定 |
|---|---|---|---|
| 新样本创建与上传 | 创建新的无敏感 110 B 文本样本，计算 SHA-256；经 FastDFS 客户端上传 | 获得新的 `group1` 逻辑路径；源文件 SHA-256 为 `23DEE594FBD814CAB59B110C1999CFCF4C0B2CFB5CF62516F4B97CDF14FA934A` | 通过 |
| 正常访问 | `curl` 请求 `localhost:8888/<逻辑路径>`，保存下载文件并计算 SHA-256 | HTTP 200，110 B，校验值与源文件一致 | 通过 |
| Storage-1 停止 | `docker stop -t 1 networkdisk-fastdfs-storage-1`；不删除卷 | Storage-1 处于停止状态；Storage-2 保持运行 | 已执行 |
| 同一路径访问切换 | Storage-1 停止后，对同一个 `localhost:8888/<逻辑路径>` 执行 `curl --connect-timeout 4 --max-time 20` | HTTP 200，耗时约 2.01 秒，110 B，SHA-256 与源文件一致 | 通过 |
| Storage-1 恢复 | `docker start networkdisk-fastdfs-storage-1`，轮询 Docker health 后再次请求同一路径 | 首个 5 秒轮询即 `healthy`；恢复后 HTTP 200，耗时约 0.006 秒，文件校验一致 | 通过 |

**中间观察：** 首次使用 PowerShell `Invoke-WebRequest` 与日志读取组合进行演练时，外层命令在停止 Storage-1 后超时；访问层日志同时出现首个上游连接超时和同请求 HTTP 200，无法单独作为充分证据。为避免把不完整命令结果写成通过，本次结论采用后续独立的短超时 `curl` 演练：该演练明确返回 HTTP 200 和下载文件校验值，作为正式证据。

**阶段结论：** 访问层故障切换验收 **通过（单 Storage-1 故障范围）**。已证明在 Storage-1 停止时，`localhost:8888` 可在约 2 秒内读取 Storage-2 上的同一副本；恢复后访问正常。

**结论边界与未验收项：**

1. 本结果不证明 Storage-2 故障、双节点同时故障、Tracker 故障、Nginx 容器故障、跨宿主机或跨机房容灾。
2. 本结果不证明 Nginx 主动健康检查、负载均衡比例或生产 SLA；本配置是被动失败重试，首次请求可承担连接超时。
3. 应用**双实例**、Dubbo/Nacos 服务治理、文件服务鉴权、数据库元数据、分片/秒传/回收站/分享等业务端到端验收仍全部未执行，严禁据此标记通过。
4. 新增测试样本仍保留在 FastDFS 命名卷中作为本次验收证据；本次未执行删除操作。
