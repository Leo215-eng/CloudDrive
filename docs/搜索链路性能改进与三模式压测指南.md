# 搜索链路性能改进与三模式压测指南

## 1. 这次为什么要改

原搜索接口只有一条生产链路：先查 Elasticsearch（ES），成功后查询 MySQL 最近 60 秒的变更并合并，ES 无结果或异常时再回退 MySQL。它保证了可用性和短期一致性，但存在四个问题：

1. 最近变更 SQL 使用 `user_id + gmt_modified`，`user_file` 缺少对应联合索引。
2. ES 和 MySQL 都查询完整结果集，没有分页上限。
3. 无法把纯 MySQL、纯 ES、生产混合链路分开，压测结果不能公平比较。
4. 60 秒补偿窗口在集中写入压测时会反复读取大量变更数据。

本次只解决这四点，不修改中文分词和父目录补全逻辑，避免同时改变太多变量。

## 2. 新同事需要先知道的概念

### 2.1 Canal 不在查询请求中

Canal 负责异步写入链路：

```text
MySQL 变更 → binlog → Canal → networkdisk-files → Elasticsearch
```

用户搜索走读取链路：

```text
HTTP 请求 → networkdisk-files → ES/MySQL → HTTP 响应
```

因此启动 Canal 不代表每次查询都会经过 Canal。Canal 的作用是维护 ES 索引。

### 2.2 为什么生产模式还要查询 MySQL

MySQL 提交与 ES 可搜索之间存在短暂异步延迟。生产模式查询 ES 后，再读取 MySQL 最近一小段时间的变更并合并，避免用户刚上传或重命名文件后暂时搜不到。

`consistency-window-ms` 是这个补偿窗口。窗口越大，一致性余量越大，但 MySQL 查询和 Java 合并的数据也越多。它必须大于实测的 Canal 同步延迟 P99。

### 2.3 P95 是什么

P95 为 69 ms 表示 95% 的请求不超过 69 ms，剩余 5% 可能更慢。对搜索接口，P95 通常比平均值更能反映用户遇到的慢请求。

## 3. 本次改动

### 3.1 最近变更联合索引

全新数据库的 `DDL_network_disk.sql` 已包含：

```sql
KEY idx_user_modified (user_id, gmt_modified)
```

已有数据库需要执行一次：

```bash
cd /data1/jinbai/NetworkDisk-main
mysql -u root -p network_disk < DDL/sql/V20260726__user_file_search_index.sql
```

执行前先确认没有同名索引：

```sql
SHOW INDEX FROM network_disk.user_file
WHERE Key_name = 'idx_user_modified';
```

如果已经有结果，不要重复执行迁移。索引会增加少量写入和磁盘成本；大表生产环境创建索引可能锁表，应安排维护窗口，本项目当前 10 万级数据可直接执行。

验证 SQL 是否使用索引：

```sql
EXPLAIN
SELECT id, filename, deleted, gmt_modified
FROM network_disk.user_file
WHERE user_id = 1
  AND gmt_modified >= NOW() - INTERVAL 5 SECOND;
```

重点检查 `key` 为 `idx_user_modified`，并观察 `rows` 是否明显小于全表数量。

### 3.2 搜索分页

请求体新增两个可选字段：

```json
{
  "keyword": "替换成当前用户确实存在的文件名关键词",
  "pageNum": 1,
  "pageSize": 20
}
```

`keyword` 只是示例，不能直接照抄“压测”。正式压测前必须用单请求确认同一关键词在 MySQL 和 ES 中都能返回数据；三轮再固定使用这个关键词。

- `pageNum` 默认 1，范围 1～100。
- `pageSize` 默认 20，范围 1～100。
- 不传字段时旧前端仍能工作。
- MySQL 使用 `LIMIT offset,pageSize`。
- ES-only 使用 Easy-ES `pageQuery`。
- production 为保证合并后分页正确，会先取得从第一页到目标页所需的 ES 数据，合并最近 MySQL 变更后再截取目标页。

当前限制最多访问前 10,000 条匹配结果，正好不超过 ES 默认 `max_result_window`。需要更深分页时再改为 `search_after`，不要提高当前上限。

### 3.3 三种搜索模式

配置项：

```yaml
com:
  disk:
    search:
      mode: production
```

| 模式 | 实际路径 | 用途 | ES 异常时行为 |
|---|---|---|---|
| `mysql-only` | 只查询 MySQL | MySQL 性能基线 | 与 ES 无关 |
| `es-only` | 只查询 ES | ES 性能基线 | 请求失败，不回退，便于暴露问题 |
| `production` | ES + 最近 MySQL 变更合并 | 真实业务链路 | 自动回退 MySQL |

模式值写错时应用会启动失败，并明确提示合法值，防止误以为自己测的是另一条链路。应用启动日志也会打印当前模式和窗口：

```text
file search configured. mode=production, consistencyWindowMs=5000
```

### 3.4 一致性窗口从 60 秒调整为 5 秒

默认配置现在是：

```yaml
com.disk.search.consistency-window-ms: 5000
```

5 秒不是永久正确值。必须实际测量：

```text
同步延迟 = ES 首次能查到记录的时刻 - MySQL 提交时刻
```

至少记录平均值、P95 和 P99。配置值应略大于 P99，例如 P99 为 2 秒时配置 3～5 秒。如果发现 Canal 堆积或 P99 超过 5 秒，启动时临时放大：

```bash
--com.disk.search.consistency-window-ms=60000
```

## 4. 构建与启动

先构建：

```bash
cd /data1/jinbai/NetworkDisk-main
mvn -pl networkdisk-business/networkdisk-files -am -DskipTests package
cd networkdisk-business/networkdisk-files
```

按要求在前台运行，使用 `Ctrl+C` 即可停止，不使用 `nohup`。

### 4.1 MySQL-only

```bash
java -jar target/networkdisk-files-1.0.0-SNAPSHOT.jar \
  --com.disk.search.mode=mysql-only \
  --easy-es.enable=false \
  --com.disk.canal.enable=false
```

### 4.2 ES-only

```bash
java -jar target/networkdisk-files-1.0.0-SNAPSHOT.jar \
  --com.disk.search.mode=es-only \
  --easy-es.enable=true \
  --com.disk.canal.enable=false
```

ES-only 压测时关闭 Canal，避免同步任务消耗资源干扰纯查询基线。压测前要先确认 ES 已有完整数据。

### 4.3 Production

```bash
java -jar target/networkdisk-files-1.0.0-SNAPSHOT.jar \
  --com.disk.search.mode=production \
  --com.disk.search.consistency-window-ms=5000 \
  --easy-es.enable=true \
  --com.disk.canal.enable=true
```

## 5. JMeter 公平压测要求

三轮只能改变 `com.disk.search.mode`，其他条件保持一致：

- 相同线程数、Ramp-up、持续时间。
- 相同关键词集合和登录用户。
- 请求体都显式传 `pageNum=1,pageSize=20`。
- 每轮重启文件服务并确认启动日志中的模式。
- 每轮开始前先预热 30 秒，正式记录 3 分钟。
- 关闭 `View Results Tree`，只保留 `Aggregate Report` 和业务成功断言。
- 压测期间不要同时批量导入或更新文件。

推荐结果表：

| 模式 | 请求数 | Average | P95 | P99 | Throughput | Error % |
|---|---:|---:|---:|---:|---:|---:|
| mysql-only | | | | | | |
| es-only | | | | | | |
| production | | | | | | |

不能用 `mysql-only` 与 `production` 直接证明 ES 比 MySQL 快。前者只有一次 MySQL 查询，后者还包含一致性补偿和结果合并。ES 与 MySQL 的引擎性能应比较 `es-only` 和 `mysql-only`；生产代价则比较 `production` 和 `es-only`。

## 6. 故障排查

### 返回结果仍超过 20 条

确认请求实际发送了 `pageSize`，并确认运行的是本次重新打包的 JAR。

### 接口返回 SUCCESS，但 JMeter 显示 100% Error

例如响应为：

```json
{"code":"SUCCESS","success":true,"message":"SUCCESS","data":[]}
```

这表示接口和鉴权成功，只是关键词没有命中。若 Response Assertion 要求 `data` 非空或匹配某个文件名，JMeter 会把所有正常的空结果标记为失败。断言只检查 `"success":true`；另外选择当前用户真实存在、且 MySQL 和 ES 都能命中的关键词，避免压测空结果这条过快且不具代表性的路径。

本项目 2026-07-28 的实际排查案例中，10 万条 `测试文件_*.txt` 属于测试账号 `123456@123.com`，而 JMeter 使用的 token 属于仅有 4 条文件的另一个账号。由于搜索按 `user_id` 隔离，请求虽然返回 `SUCCESS`，但搜索“压测”得到 `data: []`，并被旧断言全部标记为失败。修复方法是使用数据所属账号重新登录、提取该账号 token，并固定使用真实存在的关键词“测试文件”。

### MySQL 最近变更查询仍慢

执行 `SHOW INDEX` 和 `EXPLAIN`，确认已有 `idx_user_modified` 且执行计划选择了它。索引存在但未选择时，先运行 `ANALYZE TABLE network_disk.user_file;` 更新统计信息。

### es-only 直接报错

这是设计行为。该模式禁止自动回退，目的是暴露 ES 查询错误。检查 ES 容器、索引数量和服务异常日志。生产环境应使用 `production`。

### 刚修改的文件偶尔搜不到

说明 Canal 同步延迟超过当前 5 秒窗口。先临时恢复 60 秒保证正确性，再测同步 P99，最后用略高于 P99 的数值替换，不要只为了降低延迟盲目缩短窗口。
