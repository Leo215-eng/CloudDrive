# FastDFS 双 Storage 分布式存储设计方案

## 1. 目标与边界

### 真实业务场景

个人网盘用户上传照片、视频、压缩包和学习资料时，希望文件在上传后可被预览、下载、分享或在另一台设备访问。业务侧需要同时解决三类问题：

1. 文件二进制持续增长，不能挤占 MySQL 的业务查询和备份资源。
2. 单台存储节点异常不能直接导致已上传资料永久不可读。
3. 业务服务需要保存稳定的文件标识，而不是绑定某台机器的 IP 或磁盘绝对路径。

FastDFS 双 Storage 方案只解决“文件二进制存储与组内副本”问题；用户目录、权限、分享、回收站和文件元数据仍由网盘业务服务与 MySQL 管理。

### 目标

在本地 Docker 环境构建可验证的 FastDFS 存储拓扑，并让网盘文件服务通过 FastDFS 完成文件上传、下载、预览和删除。最终验证同一文件在两个同组 Storage 节点完成副本同步。

### 本阶段验收标准

1. 启动 `1 Tracker + 2 同组 Storage + Nginx`，所有容器健康运行。
2. 文件服务以 `fastdfs` Profile 启动，不再使用本地存储引擎处理业务上传。
3. 上传文件后，后端返回 FastDFS 逻辑路径（`group + path`）和可访问 URL。
4. 在两个 Storage 节点中都能找到相同文件副本；验证时允许短暂同步延迟。
5. 通过上传、访问、下载、删除四类接口完成端到端验证，并保留命令与结果记录。

### 不在本阶段实现

- Tracker、Storage 的生产集群高可用与跨机房容灾。
- ES、Canal、RocketMQ、AI、pgvector 等无关组件。
- 多设备本地目录同步、版本冲突处理和限流压测。

## 1.1 关键业务链路与异常兜底设计

| 业务场景 | 正常处理 | 异常与兜底设计 | 一致性边界 |
|---|---|---|---|
| 普通上传 | 文件服务上传二进制到 FastDFS，成功后写入文件元数据和用户文件关系。 | Tracker/Storage 超时返回可重试错误；客户端保留文件标识，后续可重新上传或走分片续传。 | 只有 FastDFS 返回逻辑路径后才创建数据库完整文件记录。 |
| 分片合并 | 合并完成后将完整文件写入 FastDFS，再写入元数据。 | 合并失败保留临时分片至过期；重试前先校验完整文件是否已存在，防止重复创建。 | 合并操作应具备幂等键：用户、文件标识与合并状态。 |
| 副本同步 | 同组 Storage 自动复制二进制文件。 | 副本存在短暂延迟时，不将“第二节点未立即出现”判为上传失败；记录副本校验任务并在超时后告警。 | 上传成功表示主 Storage 已持久化，不等价于双副本已即时确认。 |
| 下载与预览 | 使用 `group + path` 生成 Nginx 访问地址。 | HTTP 访问 404 时先检查 Nginx 映射、Storage 状态和逻辑路径；业务侧不暴露内部节点地址。 | 访问权限仍由业务服务校验，不以文件 URL 代替授权。 |
| 删除与回收站 | 先逻辑删除用户文件，进入回收站。 | FastDFS 物理删除失败时记录待清理任务并重试；不得因为回收站操作直接删除仍被其他用户引用的物理文件。 | 用户关系删除与物理文件删除分阶段执行，物理删除以“无有效引用”为前提。 |

### 可观测性要求

- 为上传、合并、删除和副本校验记录文件标识、用户标识、逻辑路径、耗时、错误码和重试次数；日志不得打印真实访问凭据。
- 记录 Tracker 不可用、Storage 下线、副本同步超时、Nginx 访问失败和物理删除重试等事件。
- 验收阶段必须以容器状态、文件校验值、接口响应和服务日志作为证据，而不是仅以“前端显示成功”为依据。

## 2. 为什么需要双 Storage

单个 Storage 只能说明系统已接入 FastDFS；两个 Storage 配置到同一 `group1` 后，上传文件会在组内复制。这样可以验证文件副本同步、单节点故障后的数据可用基础，才适合在项目中描述“分布式文件存储副本验证”。

## 3. 目标架构

```text
networkdisk-files
      │ FastDFS Client
      ▼
Tracker :22122
      │ 调度并选择 Storage
      ├───────────────┐
      ▼               ▼
Storage-1          Storage-2
group1             group1
      │ 组内副本同步  │
      └───────┬───────┘
              ▼
        Nginx :8888
              ▼
  http://localhost:8888/group1/<path>
```

### 职责划分

| 组件 | 职责 |
|---|---|
| Tracker | 管理 Storage 状态、定位可用存储节点、调度上传请求。|
| Storage | 保存文件二进制并在同组节点间同步副本。|
| Nginx | 将 FastDFS 文件路径暴露为 HTTP 访问地址，供预览和下载使用。|
| 文件服务 | 承载鉴权、业务校验、文件元数据和用户文件关系；仅保存 FastDFS 逻辑路径，不直接保存二进制。|

## 4. 现有项目基线与设计决策

### 已具备能力

- 公共文件模块已包含 `FastDFSStorageEngine`、`FastDFSStorageEngineConfig` 和文件存储抽象接口。
- 文件服务已有上传、分片上传、合并、下载和预览业务流程。
- 当前本地运行默认使用 `LocalStorageEngine`；代码中也存在面向外部 FastDFS 地址的配置示例。

### 需要确认并在实施阶段处理的设计点

1. **存储引擎选择机制**：当前本地存储实现带有 `@Primary`。实施时应改为由 Profile 或显式配置决定唯一生效的存储引擎，避免 Local、FastDFS、OSS Bean 同时参与注入。
2. **配置隔离**：新增 `application-fastdfs.yml`，仅引用环境变量或 Docker 网络地址；不得提交真实账号、密钥或生产内网地址。
3. **文件路径模型**：数据库的物理路径字段保存 `group1/M00/...` 这类逻辑路径；对前端提供的 URL 由 `outUrl + 逻辑路径` 组合生成。
4. **删除策略**：业务删除进入回收站时只变更用户文件状态；仅在物理文件不再被任何有效文件记录引用时才删除 FastDFS 文件，避免误删共享物理文件。

## 5. 实施计划（确认后执行）

### 阶段 A：基础设施

1. 新增独立的 `docker-compose.fastdfs.yml`，不改动现有 MySQL、Redis、Nacos 编排。
2. 配置 Tracker、Storage-1、Storage-2 均在同一 Docker 网络；两个 Storage 使用同一组名 `group1`。
3. 配置 Nginx 与 FastDFS HTTP 模块，统一暴露访问端口。
4. 检查 Tracker 状态和 Storage 列表，确认两个节点均为在线状态。

### 阶段 B：文件服务接入

1. 新增 `fastdfs` Profile 和本地开发配置模板。
2. 调整存储引擎装配方式，确保启用该 Profile 时只使用 `FastDFSStorageEngine`。
3. 配置 Tracker 地址、连接超时、组名和 HTTP 访问前缀。
4. 重启文件服务，验证上传、分片合并、下载和预览流程。

### 阶段 C：副本与故障验证

1. 上传带校验值的测试文件，记录 FastDFS 返回路径。
2. 分别进入 Storage-1、Storage-2 检查文件是否存在且校验值一致。
3. 暂停一个 Storage，确认另一个副本仍保留；记录实际访问表现和限制。
4. 恢复节点，确认服务重新上线且没有产生脏数据。

## 6. 资源、风险与回滚

| 项目 | 预估 / 风险 | 应对 |
|---|---|---|
| 内存 | 当前笔记本为 16 GB；FastDFS 环境应与 ES、AI、RocketMQ 分时运行。 | 实施前停止无关 Java 服务和重型容器。 |
| 镜像网络 | Docker 镜像首次拉取可能超时。 | 先验证镜像拉取，再执行编排；保留可重试命令。 |
| 副本延迟 | Storage 组内复制不是前端同步确认机制。 | 通过轮询和文件校验验证副本，不以“立即存在”作为唯一判断。 |
| 外部资源 | 现有配置含外部存储示例。 | FastDFS Profile 禁用 OSS，所有本地路径与地址隔离。 |

### 回滚方案

1. 停止 FastDFS 编排容器，不删除卷，以保留排障现场。
2. 文件服务切回 `local` Profile，恢复本地存储实现。
3. 若数据库路径记录已写入 FastDFS，不直接删除数据；先导出记录并制定迁移方案。

## 7. 完成后的简历表述边界

完成双节点副本验证后可写：

> 基于 FastDFS 搭建 1 Tracker + 2 同组 Storage 的分布式文件存储环境，完成文件上传、访问及副本同步验证；文件服务仅保存逻辑路径，实现文件元数据与二进制分离。

仍不应写“生产级高可用集群”或“跨机房容灾”，除非完成对应部署与故障验证。
